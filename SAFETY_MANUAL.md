## 1. Document Purpose

This document describes the safety architecture, usage assumptions, limitations, and operational constraints of ZenOS RTOS. It is intended for developers integrating ZenOS into embedded systems where correctness, determinism, and fault tolerance are important.

ZenOS is **not** certified to any IEC 61508, ISO 26262, or DO-178C standard. It provides safety *mechanisms* (stack canaries, MPU, watchdogs, error logging, CRC checking) that **support** building safety-relevant systems, but the integrator is responsible for validation and certification in the target domain.

---

## 2. System Overview

ZenOS is a preemptive, priority-based real-time operating system for ARM Cortex-M microcontrollers (M3, M4, M7), written in C++11 with a C-compatible API. It is built on top of the STM32 HAL and generated by STM32CubeMX.

### 2.1 Supported Hardware

| Family     | Cores | Flash (typ.) | RAM (typ.) | Max MPU Regions |
|------------|-------|--------------|------------|-----------------|
| STM32F1xx  | 1     | 64 KB        | 20 KB      | 8 (Cortex-M3)   |
| STM32F2xx  | 1     | 1 MB         | 128 KB     | 8               |
| STM32F4xx  | 1     | 1 MB         | 128 KB     | 16              |
| STM32F7xx  | 1     | 2 MB         | 256 KB     | 16              |
| STM32H7xx  | 2     | 2 MB         | 256 KB     | 16              |
| STM32G4xx  | 1     | 512 KB       | 96 KB      | 16              |
| STM32L0xx  | 1     | 128 KB       | 20 KB      | 8               |
| STM32L4xx  | 1     | 1 MB         | 128 KB     | 16              |
| STM32WBxx  | 1     | 1 MB         | 256 KB     | 16              |
| STM32G0xx  | 1     | 128 KB       | 20 KB      | 8               |

> **Note:** Other ARM Cortex-M targets are supported via the generic fallback (`OS_FAMILY_NAME = "Generic Cortex-M"`). Auto-detected features (MPU region count, flash/RAM sizes) must be verified manually on non-STM32 targets.

### 2.2 Architecture Summary

- **Scheduler:** O(1) preemptive priority-based with hardware-assisted context switch (PendSV + PSP)
- **Tasks:** Static allocation, template-based creation, priority 0–255
- **IPC:** Events, recursive mutexes with Immediate Priority Ceiling (IPC), counting semaphores, bounded FIFO queues
- **Tickless Idle:** WFI-based sleep for power savings (optional)
- **SMP:** Dual-core support for STM32H7xx (optional, currently single-core on other families)

## 3. Safety Mechanisms

ZenOS provides the following compile-time configurable safety mechanisms. All are enabled by default in `ZenOS_Config.hpp` and can be individually disabled.

### 3.1 Stack Overflow Detection (`OS_SAFETY_SOFT_WATCHDOG`)

**Mechanism:** Canary-based + stack pointer bounds checking. Each task stack is initialized with a known canary pattern (`0xDEADBEEF`) in the lowest 8 words. During each tick, `os_stack_check_all()` verifies:

1. **Stack pointer** has not dipped below the canary region (true overflow)
2. **Canary words** have not been corrupted (external memory corruption)

**Response:** On overflow detection, the affected task is removed from the priority queue and reset (up to `OS_SAFETY_TASK_MAX_RECOVERY` times, default 3). If recovery is exhausted, the task is permanently deactivated.

**Assumption:** Stack overflow detection is *reactive* — it runs periodically in the tick handler. A catastrophic overflow that corrupts adjacent TCB memory before the next check will go undetected. Stack sizes must be designed with sufficient margin (recommend ≥30% headroom over peak usage).

**Limitation:** The canary region occupies the bottom 32 bytes of each stack. Reducing stack size below ~64 bytes (16 words) will leave insufficient room for the canary plus any actual stack usage.

### 3.2 TCB Integrity Check (`OS_MONITOR_TCB_INTEGRITY`)

**Mechanism:** A magic number (`0x54434200` / "TCB\0") is written to each TCB at creation and validated during stack checks. If the magic is corrupted, the task is deactivated rather than reset (too risky to reset a corrupted TCB).

**Assumption:** This detects *some* memory corruption. It does not protect against all possible TCB corruption patterns — only those that happen to preserve the magic word by chance.

### 3.3 Deadline Monitoring (`OS_MONITOR_DEADLINE`)

**Mechanism:** Each task can have a deadline (in ms). If the task does not execute within its deadline window, the OS logs a `DEADLINE_MISS` error and takes the configured action.

**Configurable actions** (`OS_SAFETY_DEADLINE_ACTION`):
- `0` — Log only (no task action)
- `1` — Reset the task (default)
- `2` — Permanently disable the task

**Assumption:** Deadlines must be set to values greater than one tick period (`OS_KERNEL_TICK_PERIOD_US`). Setting a deadline shorter than the tick period will cause immediate miss on every tick.

**Limitation:** Deadline monitoring is cooperative — it detects *whether* the task ran, not *what* it did. A task that runs but does not complete its work within the deadline window will not be detected unless it also fails to yield back within the deadline.

### 3.4 Error Logging (`OS_MONITOR_ERROR_LOG`)

**Mechanism:** A fixed-size ring buffer (`OS_MONITOR_ERROR_LOG_SIZE`, default 32 entries) records errors with:
- Timestamp (tick count)
- Error code (enum `OSError`)
- Task ID of the offending task
- Severity level (INFO, WARNING, CRITICAL)

**Assumption:** The ring buffer overwrites old entries when full. In a continuous production system, errors must be retrieved (e.g., via UART, flash logging) before they are lost.

**Limitation:** The error log does not survive a hardware reset. If the MCU resets due to a watchdog or HardFault, all logged errors are lost unless separately persisted to non-volatile storage.

### 3.5 Hardware Watchdog (`OS_SAFETY_HW_WATCHDOG`)

**Mechanism:** Integration with the STM32 IWDG (Independent Watchdog). Provides two feed functions:

- `os_hw_watchdog_feed()` — Unconditional feed (system is healthy)
- `os_hw_watchdog_check()` — Conditional feed: only feeds if `error_count < 10` and the scheduler is running

If the system is unhealthy (too many errors), the watchdog is not fed and the MCU resets.

**Assumption:** The IWDG is configured by CubeMX with a known timeout window (~6.5s on the test hardware). The integrator **must** ensure that the IWDG feed task runs frequently enough to prevent spurious resets during normal operation. A task that blocks for longer than the IWDG timeout without another task feeding the watchdog will cause a reset.

**Limitation:** The hardware watchdog is an external reset mechanism — it does not perform graceful shutdown. All volatile state is lost on reset. The integrator must design recovery logic (e.g., save state to flash before reset, use reset reason flags in `RCC->CSR`).

### 3.6 Software Watchdog (`OS_SAFETY_SOFT_WATCHDOG`)

**Mechanism:** Detects stuck tasks by monitoring `last_yield_tick`. If a task has not yielded within `OS_SAFETY_SOFT_WDG_TIMEOUT_MS` (default 3000ms), it is considered stuck and reset.

**Assumption:** Tasks are expected to either yield (`os_yield()`, `os_delay_ms()`, or block on IPC) within the timeout period. A task performing a long computation without yielding will be detected as stuck, even if it is legitimately busy.

**Limitation:** If a task performs exactly one yield per timeout period, the watchdog will not trigger even if the task is functionally stuck (e.g., stuck in an infinite loop with periodic yields). The integrator must design tasks to yield *frequently*.

### 3.7 RAM Test (`OS_SAFETY_RAM_TEST`)

**Mechanism:** Background March C- algorithm that tests SRAM integrity one word at a time. Each call to `os_ram_test_step()` tests one 32-bit word. The test covers RAM from `OS_RAM_TEST_START` to `OS_RAM_TEST_END` (middle 50% of SRAM, skipping the first 16 KB for stack/BSS/data).

**Assumption:** The test is *non-destructive* — it reads, writes complement, reads complement, then restores the original value. However, during the write-read-restore cycle, the word is temporarily modified. If an interrupt or DMA reads that exact word during the cycle, data corruption may occur.

**Limitation:**
- The test only covers the *middle* portion of RAM. Stack and BSS regions are not tested.
- The test runs at the rate of one word per call. For a 20 KB STM32F1 RAM, the test region is approximately 2 KB (512 words). At one step per call, at least 512 calls are needed to complete one pass. Call `os_ram_test_step()` from the idle task or a low-priority background task.
- SRAM with single-bit errors may not be detected (March C- is designed for stuck-at faults, not bit-flips).

### 3.8 CRC ROM Integrity Check (`OS_SAFETY_CRC_CHECK`)

**Mechanism:** At boot, `os_crc_init()` computes a CRC over the entire flash region using the STM32 CRC peripheral. Subsequent calls to `os_crc_check_step()` re-CRC the flash in 64-word chunks and compare against the expected value. A mismatch triggers `HARDFAULT` error reporting.

**Assumption:** The flash contents must not change between `os_crc_init()` and `os_crc_check_step()`. If the application writes to flash (e.g., OTA updates, EEPROM emulation) while the CRC check is in progress, the check will produce false positives.

**Limitation:**
- The CRC check uses a single polynomial (hardware CRC). It provides a probabilistic check, not a cryptographic guarantee.
- The check runs incrementally to bound ISR/CPU budget. A full re-check takes multiple calls.

### 3.9 MPU Protection (`OS_SAFETY_MPU`)

**Mechanism:** Hardware Memory Protection Unit (ARMv7-M) configured with static regions:
- Region 0: Flash (code) — read-only, executable
- Region 1: SRAM (data) — read/write, non-executable
- Region 2: Peripherals — read/write, non-executable
- Region 3: Per-task stack — read/write, non-executable
- Regions 4+: Extra per-task regions (configurable via `os_mpu_add_region()`)

Tasks run unprivileged (`CONTROL.nPRIV = 1`). The kernel, idle task, and ISRs run privileged and bypass the MPU via `PRIVDEFENA`.

**Assumption:** MPU regions are set at task context switch time. The MPU cannot protect against:
- Violations within a single task (e.g., a task corrupting its own stack)
- Violations during interrupt handling (ISRs run privileged)

**Limitation:**
- Cortex-M3 has only 8 MPU regions; Cortex-M4/M7 have 16. Complex systems with many tasks may exhaust available regions.
- MPU regions must be power-of-2 sized and aligned. Granularity is limited.
- The MPU does not provide execute-only or write-only protection — only RO, RW, and XN combinations.
- Nested interrupts and context switches create brief windows where MPU configuration is changing. During these windows, protection is temporarily relaxed.

### 3.10 Critical Section Timeout (`OS_SAFETY_MAX_CRITICAL_US`)

**Mechanism:** `OS_SAFE` blocks (interrupt-disable regions) are timed via the DWT cycle counter. If a critical section exceeds `OS_SAFETY_MAX_CRITICAL_US` (default 1000 µs), a `SAFE_TOO_LONG` error is reported.

**Assumption:** The DWT cycle counter (`CYCCNT`) must be available and enabled. On Cortex-M3/M4/M7, DWT is available by default. The system clock frequency must be known to convert cycles to microseconds.

**Limitation:** The timeout is a *diagnostic* — it reports the error but does not automatically break the critical section. A stuck critical section will continue to hold interrupts disabled.

### 3.11 Fault Handler (`OS_Fault_Handler`)

**Mechanism:** All fault exceptions (HardFault, MemManage, BusFault, UsageFault) are caught by `OS_Fault_Handler`, which:
1. Reports `HARDFAULT` error
2. Resets the safe depth to 0
3. Deactivates the current task
4. Restores the idle task and triggers a context switch

**Assumption:** After a fault, the system continues running with the offending task deactivated. The system is in a degraded state. The integrator should log the fault and, if possible, trigger a controlled reset.

**Limitation:** The fault handler uses the idle task's stack for recovery. If the fault corrupted the idle stack (unlikely but possible), recovery may fail. The fault handler also disables interrupts briefly — this is acceptable only if the system can tolerate a short interrupt blackout.

## 4. Usage Assumptions

### 4.1 Task Creation

- **All tasks must be created before `os_start()` is called.** Tasks cannot be created dynamically after the scheduler starts. Calling `_os_task_create_internal()` after `os_start()` will return -1.
- Tasks are statically allocated (template-based). Each task's TCB and stack are allocated at compile time.
- Task priorities must be unique for tasks that need preemption ordering. Equal-priority tasks are not round-robin scheduled (the scheduler is priority-based, not time-sliced).

### 4.2 Stack Sizing

- Default stack size is `OS_KERNEL_STACK_SIZE = 512` bytes (configurable).
- Stack usage varies by compiler optimization level, HAL library depth, and ISR nesting.
- **The stack watermark report** (`os_get_stack_usage()`, `os_get_stack_report()`) should be used during development to measure actual peak usage, then the stack size should be set to ≥130% of peak usage.
- RTOS tasks that call HAL functions, use floating-point, or deeply nested function calls require larger stacks.

### 4.3 Interrupt Handling

- ISRs that use OS IPC (`os_event_signal_from_isr()`, `put_from_isr()`, `signal_from_isr()`) must use the ISR-safe variants. Calling task-level IPC functions from an ISR results in undefined behavior.
- `OS_SAFE` should be used to protect shared variables between tasks and ISRs.
- ISRs run unprivileged only if explicitly configured. By default, ISRs run privileged and bypass the MPU.

### 4.4 IPC Usage

- **Events:** Accumulated signal counts. Multiple signals before a single `wait()` will be consumed sequentially. Events with ID ≥ 32 must be signaled individually (not via mask-based `signal_from_isr(uint32_t mask)`).
- **Mutexes:** Recursive locking is supported but the unlock count must match the lock count. Double-unlocking an unlocked mutex is tolerated but increments the error counter.
- **IPC Ceiling (Priority Inheritance):** Set the ceiling priority to the priority of the highest-priority task that will ever lock the mutex. An incorrect ceiling can lead to priority inversion or priority conflicts.
- **Queues:** Capacity is fixed at compile time (template parameter). `put_from_isr()` is ISR-safe but does not block (returns false if full).
- **Semaphores:** Max count limits the signal count. `signal()` returns false if the semaphore is at max count.

### 4.5 Tick Resolution

- The tick period is configured via `OS_KERNEL_TICK_PERIOD_US` (default 100 µs, i.e., 10 kHz tick rate).
- `os_delay_ms()` resolution is limited by the tick period. A delay of 1 tick may be shorter than the configured ms value.
- `os_delay_us()` uses busy-waiting (DWT cycle counter) for sub-tick delays. This blocks the CPU and is not suitable for long delays.

### 4.6 Memory

- ZenOS uses only static allocation. There is no heap, no `malloc()`/`new`, and no dynamic memory fragmentation.
- Task stacks, TCBs, event control blocks, and error logs are allocated at compile time.
- The event pool size is fixed (`OS_EVENT_POOL_SIZE`).

### 4.7 Compiler and Optimization

- ZenOS is tested with GCC (`arm-none-eabi-gcc`). Other compilers (ARM CC, IAR, Clang) are not officially supported.
- Tested at `-O0`, `-O1`, `-O2`, `-O3`, `-Os`. Stack sizes must be verified at the target optimization level, as `-O2` and above may inline HAL frames deeper.
- `static_assert` verifies TCB layout at compile time. Reordering TCB fields will cause a compile error.

## 5. Limitations

### 5.1 Architectural Limitations

| Limitation | Impact | Mitigation |
|---|---|---|
| No dynamic task creation after `os_start()` | Cannot spawn tasks at runtime | Pre-create all tasks with `os_task_create_st()` and start/stop as needed |
| No round-robin scheduling | Equal-priority tasks must yield manually | Use `os_yield()` in cooperative tasks at the same priority |
| No mutex priority inheritance across IPC boundaries | A chain of mutex acquisitions does not propagate the ceiling transitively | Keep critical sections short; avoid holding multiple mutexes |
| Single-core only (except STM32H7) | No true parallelism on single-core MCUs | Leverage ISRs for high-priority concurrent work |
| No dynamic memory allocation | Cannot resize queues, stacks, or task lists at runtime | Over-provision at compile time; use the stack report to calibrate |
| No message priority (FIFO only) | Cannot prioritize urgent messages in a queue | Use separate queues for different priority levels |
| Tick-based timing only | Minimum resolution is `OS_KERNEL_TICK_PERIOD_US` | Use `os_delay_us()` for sub-tick busy-waits; avoid for long durations |

### 5.2 Safety Mechanism Limitations

| Mechanism | Limitation | Consequence |
|---|---|---|
| Stack canary | Reactive (checked in tick handler) | Overflow between checks goes undetected |
| TCB magic | Only detects 4-byte corruption of specific field | Corruption that preserves the magic word is invisible |
| Deadline monitor | Detects non-execution, not non-completion | A task that runs but does not finish work is not detected |
| RAM test | Non-destructive write during ISR/DMA access | False positives possible during active DMA transfers |
| RAM test | Tests only middle 50% of SRAM | Stack and BSS corruption is undetected by RAM test |
| Hardware watchdog | External reset on timeout | No graceful shutdown; volatile state lost |
| MPU | Brief unprotected windows during context switch | Race conditions possible during MPU reconfiguration |
| CRC check | Incremental (not atomic) | Flash writes during check cause false positives |
| Error log | Ring buffer, RAM-only | Lost on hardware reset |

### 5.3 Known Edge Cases

1. **Double unlock:** Tolerated but increments error count. Does not corrupt mutex state.
2. **Create after start:** Returns -1 and reports `TASK_AFTER_START`. No crash.
3. **Event signal with invalid ID:** Reports `INVALID_EVENT_ID` and increments error count.
4. **Queue/semaphore timeout on empty/full:** Returns false with no crash. The caller should handle the timeout explicitly.
5. **OS_SAFE nested:** Supported (tracks depth). Deeply nested critical sections (>1 ms) trigger `SAFE_TOO_LONG` diagnostic.
6. **IPC ceiling = 0:** Disables priority boosting. The mutex operates as a plain lock with no inversion protection.

### 6.5 Safety Standard Enforcement (IEC 62304 / IEC 61508)

ZenOS provides two compile-time enforcement macros that validate safety configurations against the applicable standard. When enabled, the build will **fail with a `#error`** if any mandatory configuration is disabled.

#### 6.5.1 Enabling Enforcement

Set these macros via compiler `-D` flags. **Do not define them in `ZenOS_Config.hpp`** — override them in your build system or project settings.

```bash
# IEC 62304 — Medical device software lifecycle
# Values: 0 (disabled), 1 (Class A), 2 (Class B), 3 (Class C)
-DMEDICAL=2

# IEC 61508 — Industrial functional safety
# Values: 0 (disabled), 1 (SIL 1), 2 (SIL 2), 3 (SIL 3), 4 (SIL 4)
-DINDUSTRIAL=3
```

Both macros can be combined — the **stricter** requirement applies.

#### 6.5.2 IEC 62304 Medical Software Safety Classes

| Class | Risk Level | Description |
|-------|-----------|-------------|
| **A** | No injury possible | Informational / non-critical software |
| **B** | Non-serious injury possible | Software whose failure could cause minor injury |
| **C** | Death or serious injury possible | Software whose failure could cause life-threatening injury |

#### 6.5.3 IEC 61508 Safety Integrity Levels

| SIL | Risk Level | Description |
|-----|-----------|-------------|
| **1** | Low | Basic fault detection required |
| **2** | Medium | Robust fault detection + corrective action |
| **3** | High | High-integrity fault tolerance + spatial isolation |
| **4** | Very high | Highest integrity — typically hardware, not SW |

#### 6.5.5 Example Build Configurations

**Medical Class C (life-critical device):**
```makefile
CFLAGS += -DMEDICAL=3
# All safety features must be enabled (default).
# If any is disabled, the build will fail.
```

**Industrial SIL 2 (process control):**
```makefile
CFLAGS += -DINDUSTRIAL=2
# Requires: DEADLINE, MUTEX, HW_WATCHDOG, ERROR_LOG,
#           SOFT_WATCHDOG, DEADLINE_ACTION ≥ 1
```

**Medical Class C + Industrial SIL 3 combined:**
```makefile
CFLAGS += -DMEDICAL=3 -DINDUSTRIAL=3
# The union of both requirements applies.
# All safety features must be enabled.
```

**Non-safety application (no enforcement):**
```makefile
# Neither macro defined — all features optional.
# CFLAGS += (no -DMEDICAL= or -DINDUSTRIAL= needed)
```

#### 6.5.6 Important Notes

- **This is not certification.** The macros enforce *configuration completeness*, not compliance. The integrator must still perform the full safety lifecycle (risk analysis, V&V, documentation) per the applicable standard.
- **Default values already satisfy all levels.** Since all safety features are enabled by default, the macros will only trigger `#error` if you *disable* a feature that the standard requires.
- **The macros validate only configuration.** They do not verify runtime behavior, task timing analysis, or stack sizing — these must be validated separately.
- **IEC 62304 §5.5** requires that safety-related software changes be subject to configuration management. Changing these macros constitutes a configuration change that must be documented.

## 7. Recommended Integration Practices

1. **Measure stack usage** with `os_get_stack_usage()` and `os_get_stack_report()` during development. Set stack sizes to ≥130% of measured peak.
2. **Feed the hardware watchdog** from a dedicated task with a period ≤ 50% of the IWDG timeout.
3. **Use `os_error_expect_begin()`/`os_error_expect_end()`** around known-safe error paths (e.g., testing) to keep unexpected error counts accurate.
4. **Periodically read the error log** (`os_get_error_log_entry()`) and persist to non-volatile storage if the system must survive resets.
5. **Run the RAM test in idle** by calling `os_ram_test_step()` from the idle task hook. Monitor `os_get_ram_test_error_count()`.
6. **Call `os_crc_init()` once at boot**, then call `os_crc_check_step()` periodically from a background task.
7. **Set IPC ceiling priorities correctly** — set each mutex's ceiling to the maximum priority of any task that acquires it.
8. **Disable unused features** in `ZenOS_Config.hpp` to reduce flash/RAM footprint on constrained devices.

## 8. Error Codes Reference

| Code | Enum | Description | Typical Cause |
|---|---|---|---|
| 1 | `SAFE_DELAY_MS` | Delay called inside OS_SAFE | Bug: blocking call in critical section |
| 2 | `SAFE_YIELD` | Yield called inside OS_SAFE | Bug: yield in critical section |
| 3 | `SAFE_EVENT_WAIT` | Event wait inside OS_SAFE | Bug: blocking IPC in critical section |
| 4 | `STACK_OVERFLOW` | Stack canary or SP check failed | Task stack too small |
| 5 | `INVALID_EVENT_ID` | Event signal with out-of-range ID | Bug: uninitialized or invalid event |
| 6 | `TASK_AFTER_START` | Task creation after os_start() | Bug: create after scheduler started |
| 7 | `TASK_STUCK` | Software watchdog timeout | Task not yielding within timeout |
| 8 | `SAFE_TOO_LONG` | OS_SAFE exceeded max duration | Bug: long critical section |
| 9 | `HARDFAULT` | CPU fault exception | Memory access violation, invalid instruction |
| 10 | `PRIORITY_CONFLICT` | Mutex ceiling conflict detected | Misconfigured ceiling priority |
| 11 | `DEADLINE_MISS` | Task missed its deadline | Task overloaded or blocked too long |
| 12 | `TCB_CORRUPTED` | TCB magic number invalid | Memory corruption |
